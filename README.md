# AL-MOTAMAYEZ

واجهة عربية لإدارة مصنع الملابس، مع مصادقة وطلبات حسابات وأوامر تشغيل ومراحل إنتاج وسجلات مرنة مشتركة بين الأجهزة عبر Supabase.

## إعداد Supabase

1. افتح SQL Editor في مشروع Supabase وشغّل الملف كاملًا `supabase/schema.sql`؛ ينشئ جداول `users`, `factory_clients`, `orders`, `production_stages`, `factory_records`, `factory_fabrics`, `factory_fabric_transactions`, `factory_order_expenses` و`factory_cash_transactions` والسياسات والدوال المطلوبة، فلا يلزم إنشاؤها يدوياً جدولاً جدولاً. اسم الموديل ورقمه محفوظان مباشرة في كل طلبية ولا يعتمد النظام على جدول موديلات منفصل.
   إذا وجد جدول `users` القديم الذي يحتوي كلمة مرور نصية، يحفظ السكربت حقول الملف الشخصي غير الحساسة في `users_legacy_profiles` بعد حذف عمود كلمة المرور، ثم يربط الملفات التي لها حساب Auth مطابق. تبقى الملفات غير المرتبطة في الأرشيف الخاص، ولا تُنقل أي كلمة مرور إلى النظام الجديد. احتفظ بنسخة احتياطية قبل تشغيل ترحيل بنيوي على قاعدة الإنتاج.
2. من **Authentication → Providers → Email** عطّل **Confirm email**. نموذج التسجيل لا يجمع بريدًا إلكترونيًا، لذلك يستخدم النظام عنوانًا داخليًا ثابت النطاق مشتقًا من اسم المستخدم؛ لا يمكن تأكيده برسالة بريد.
3. من **Authentication → Users** تأكد من وجود مستخدم الأدمن مع تفعيل **Auto confirm user**:
   - البريد: `mohamed01007033454@gmail.com` (يدعم النظام أيضاً العنوان الداخلي القديم `zero0@accounts.al-motamayez.invalid`)
   - عيّن كلمة المرور المطلوبة من المالك مباشرةً في لوحة Supabase، ولا تحفظها في ملفات المشروع.
4. أعد تشغيل `supabase/schema.sql` لإضافة/ترقية ملف الحساب المرتبط بهذا المستخدم تلقائيًا إلى `admin` و`active`. يجب أن يكون مستخدم Auth موجودًا مسبقًا؛ المخطط لا ينشئ حساب مصادقة أو كلمة مرور. بعد المصادقة، يمكن لحساب الأدمن المؤكد فقط استعادة ملفه عبر `ensure_factory_admin_profile` إذا كان مفقودًا، دون تعطيل RLS.
5. أكمِل إنشاء الأدمن وترقيته قبل نشر الواجهة. انشر مجلد المشروع عبر خادم صفحات ثابتة أو استضافة HTTPS وافتح `index.html`. لا تستخدم `file://` لتشغيل طلبات Supabase.

وجود صف `ZERO0` في `public.users` وحده لا ينشئ مستخدمًا في Supabase Auth ولا يسمح بتسجيل الدخول. يجب وجود مستخدم Auth بالبريد المرتبط بالأدمن وأن يشير `public.users.id` إلى معرّف مستخدم Auth نفسه. لا تحاول مقارنة كلمة المرور من المتصفح أو تخزينها في `public.users`.

يستخدم `js/supabase-config.js` عنوان المشروع ومفتاح النشر العام (publishable key). المفتاح العام مخصص للواجهة؛ لا تضع `service_role` أو أي مفتاح سري في ملفات المشروع. لا تنشئ الواجهة جداول أو أعمدة SQL تلقائياً؛ أي تغيير مستقبلي في الحقول المرنة يحفظ كقيمة JSONB داخل `factory_records.payload` ولا يحتاج عموداً جديداً. تبقى الجداول العلائقية الأساسية ثابتة ومقيدة، ويتطلب تغيير بنيتها ترحيلاً مقصوداً. إبقاء RLS مفعّلاً ضروري لمنع الزوار من قراءة أو تعديل حسابات المصنع.

## الحسابات والصلاحيات

- الدخول باسم المستخدم وكلمة المرور. يحول العميل اسم المستخدم إلى عنوان Auth داخلي؛ رقم الهاتف مطلوب عند التسجيل ويحفظ كبيانات ملف شخصي فقط، ولا يرسل النظام SMS.
- تحفظ جلسة Supabase تلقائيًا في `localStorage` مع تحديث رمز الجلسة؛ خيار «البقاء مسجلاً للدخول» في صفحة الدخول يحفظ الجلسة في هذا الجهاز، وإلغاء اختياره يحفظها في `sessionStorage` حتى إغلاق جلسة المتصفح. إذا بقيت الجلسة صالحة، يعيد فتح صفحة الدخول توجيه المستخدم إلى لوحته تلقائيًا.
- يمكن للأدمن تسجيل الدخول باسم `ZERO0` أو ببريده المسجل في Supabase Auth؛ يحول النموذج `ZERO0` إلى `mohamed01007033454@gmail.com`، ويعطي النظام هذا البريد أولوية على اسم المستخدم الوصفي في Auth metadata. يجب أن تكون كلمة المرور هي كلمة مرور Supabase Auth، وأن يطابق `users.id` معرّف حساب Auth؛ صف users وحده لا يصادق الدخول.
- تتيح صفحة الدخول طلب رابط إعادة تعيين كلمة المرور إلى بريد Auth، ثم حفظ كلمة مرور جديدة بعد فتح الرابط. يجب إضافة عنوان صفحة الدخول المنشورة (والمحلي عند التطوير) إلى قائمة Redirect URLs المسموح بها في Supabase Auth.
- التسجيل الخارجي ينشئ مستخدم Auth ويبقي ملفه في `users` بحالة `pending` ودون دور فعال، ويُعرض للمتقدم إشعار بأن الحساب ينتظر موافقة الإدارة. لا تفتح بوابة العميل قبل الموافقة. تعرض لوحة الإدارة الطلبات وتتيح اعتماد العميل بربطه بملف موجود غير مرتبط، أو إنشاء ملف عميل جديد مرتبط تلقائياً. ويمكن للأدمن من تفاصيل أي ملف عميل ربط حساب عميل نشط أو تسجيل معلق؛ اعتماد التسجيل والربط ينفذان ذرياً عبر `admin_link_factory_client_account` مع التحقق من دور الأدمن ومن عدم ربط الحساب أو الملف بعميل آخر. عند الربط بملف قائم، تتم مزامنة معرف الحساب للطلبات والدفعات والتصفيات وطلبات الموديلات المرتبطة بمعرف الملف، مع إبقاء معرفات السجلات والتفاصيل المالية والتواريخ كما هي؛ كما يعيد تشغيل `supabase/schema.sql` مزامنة الملفات التي رُبطت قبل هذا التحديث. أما تفعيل حساب العامل أو المشرف فيبقى ضمن مسار اعتماد الأدوار الوظيفية.
- جدول `users` يحفظ الاسم واسم المستخدم والبريد ورقم الهاتف والدور والحالة؛ البريد يُزامن مع حساب Supabase Auth، وكلمات المرور تبقى في Auth ولا تُخزّن أو تُرسل ضمن بيانات المستخدم الوصفية أو تعرض في لوحة الإدارة.
- يقرأ الأدمن الطلبات المعلقة من جدول `users`؛ يعتمد تسجيل العميل بربطه بملف قائم أو بإنشاء ملف جديد، بينما يختار الدور الوظيفي عند اعتماد العامل أو المشرف. سياسات RLS تمنع المستخدم من تغيير دوره أو حالته بنفسه.
- يمكن للأدمن تعليق حساب نشط وإعادة تفعيله من جدول المستخدمين. تفحص صفحة الدخول الحالة وتمنع التوجيه للحساب المعلق، كما تمنع سياسات قاعدة البيانات صلاحيات الأدوار للحساب الموقوف.
- حذف المستخدم من لوحة الإدارة يستدعي `public.delete_user_by_admin(target_user_id)`؛ تتحقق الدالة من صلاحية الأدمن النشط وتحمي حسابات الإدارة، بينما لا يُمنح العميل صلاحية حذف مباشرة من `public.users`. يحذف الإجراء صف الملف الشخصي فقط ولا يحذف حساب Supabase Auth. قيد `orders.client_id` مضبوط على `ON DELETE SET NULL` حتى تبقى الطلبات والتسليمات محفوظة عند حذف ملف المستخدم؛ يعيد ترحيل المخطط ضبط القيود القديمة على هذا العمود.
- يمكن حذف ملف العميل من بطاقة العميل أو قائمة الملفات عبر `public.delete_factory_client(requested_client_id)` بعد حذف صف حساب الدخول المرتبط إن وجد؛ ترفض الدالة حذف الملفات التي لها طلبات أو تسليمات أو حركات مالية أو مخزون، حفاظاً على سجل التشغيل والحساب.
- زر مسح النظام موجود ضمن قسم «طلبات مستخدمي النظام» ويستدعي `public.reset_factory_data()` كعملية ذرّية بصلاحية أدمن. تمسح الدالة سجلات التشغيل والمخزون والحسابات والحركات وتحذف حسابات Supabase Auth الأخرى مع إبقاء حساب الأدمن الحالي؛ تُحذف صور الموديلات بعدها عبر Supabase Storage API، وفق سياسة حذف للأدمن فقط. شغّل المخطط لتفعيل الدالة والسياسة.
- تستخدم صفحات الدخول ولوحات التحكم نوافذ تأكيد وإشعارات مخصصة من `js/ui.js` بدل نوافذ المتصفح الافتراضية.
- لوحة الإدارة تعرض كل قسم في القائمة الجانبية، ويحتوي قسم «الموديلات والطلبيات» على تبويبين داخليين: قائمة الموديلات وإدارة حالاتها. تعرض بطاقات الطلبية اسم الموديل كاملاً والعدد وسعر القطعة والإجمالي، وتتيح إضافة بنود مصروفات خارجية تراكمية دون الكتابة فوق البنود السابقة. يعرض تفصيل الموديل كروت المقاسات والألوان منفصلة ويحافظ على تكرار المقاس؛ ويُنشأ كود العميل تلقائياً أو يدوياً، ورقم الموديل التسلسلي عام ومتزايد ويظهر ككود مصنع من نمط `A-1`، بينما يبقى كود العميل مستقلاً. يجمع قسم «إدارة العملاء» الحسابات وملفات العملاء بتبويبين، وتعرض بطاقات الملخص الحالات ومعاينات قابلة للفتح؛ يمكن تعديل بيانات المحل والتواصل من الملف دون إنشاء حساب دخول تلقائياً. تعرض لوحة التحكم النقدية الحالية في الدرج، ومديونيات العملاء عن البضاعة المسلّمة، وقيمة البضاعة التي لم تُسلّم بعد؛ وتتحدث المؤشرات مع أحداث Realtime للمدفوعات والتسليمات والحركات النقدية وسُلف العمال والمبالغ المصروفة فعلياً من الرواتب. توجد داخل قسم المالية تبويبات للدفعات وسجل «الداخل والخارج»، ويشمل السجل الحركات النقدية ودفعات العملاء وسُلف العمال والمبالغ المصروفة فعلياً من الرواتب. يعمل جرس التحديثات وحالة المتصلين عبر Supabase Realtime Presence وPostgres Changes؛ وتُحفظ إشعارات كل حساب وحالة قراءتها محلياً في المتصفح. لا يغيّر تقدم القص حالة الطلب تلقائياً.
- قسم «شؤون العمال والحضور» للإدارة يتضمن تبويب «العاملين» مع زر إنشاء ملف عامل مستقل، وملفات قابلة للطباعة تضم تبويبي «المستحقات والماليات» و«البيانات الشخصية». لا يُنشأ ملف عامل من التسجيل الخارجي؛ ينشئ الأدمن الملف ويربط به حساباً وظيفياً معلقاً من النموذج، كما يمكن فك الربط من الملف مع إبقاء سجلات العامل. قائمة العاملين مبنية على الملفات المسجلة فقط، وتعرض المسمى الوظيفي الفعلي. أجر اليوم للراتب الشهري = الراتب ÷ 30، وللأسبوعي = الراتب ÷ 7؛ أجر الساعة = أجر اليوم ÷ 9، وتستخدم الأسعار الناتجة في خصومات الوقت والجزاءات والسهر. أول تسجيل للحضور يستخدم بداية الدوام الافتراضية، وأول تسجيل للانصراف يسجل الوقت الحالي؛ ويمكن تعديل الوقتين مستقلاً. تسجيل التأخير يطلب قرار الأدمن (اللائحة، الوقت الفعلي، أو الإعفاء) وتظل النافذة ظاهرة حتى حفظ القرار أو إغلاقها. تُضاف بنود الخصم ومبالغها يدوياً من الإعدادات، وتُضاف قواعد التأخير أو تعدل أو تحذف ديناميكياً؛ لا توجد قائمة جزاءات افتراضية. الغياب يطلب اختياراً صريحاً بين الإذن (خصم يوم) وعدم الإذن (لا يُحتسب اليوم ضمن الأجر مع خصم جزاء يوم عمل واحد). لا تُحتسب الجمعة مدفوعة تلقائياً إلا بعد تسجيل حضور السبت التالي، ويمكن للأدمن تعديلها يدوياً. أجر السهر يحسب بمضاعف افتراضي 1.5 قابل للضبط. تبقى تصفية الشهر السابق غير متاحة حتى اليوم الخامس من الشهر التالي، ولا يُرحّل الرصيد لمجرد بدء شهر جديد؛ يُرحّل عند حفظ التصفية. تعرض بوابة العامل ملخص المستحقات والسلف والصافي وسجلات الشهر الحالي للحضور والجزاءات والسهر؛ بياناتها محدودة بسجلات الحساب المرتبط عبر سياسات RLS. شغّل `supabase/schema.sql` بعد تحديث سياسة قراءة السجلات لتفعيل وصول العامل إلى ملفه وسجلاته فقط. تُحفظ ملفات العاملين والأجور والحضور والمخالفات والتصفيات في مجموعات مستقلة من `factory_records`؛ يلزم إدخال أجر العامل ومراجعة سياسة المصنع قبل اعتماد حساب نهائي.
- تستخدم مؤشرات الإدارة وملفات العملاء ولوحات القص والخياطة مجمّع حالات موحداً: «قبل القص»، «في انتظار الخياطة»، «قيد الخياطة / جاري الخياطة»، و«ما بعد الخياطة». شارات الموديلات تستخدم `orders.status` كالحالة الأساسية، وتقدّم حالة مرحلة الخياطة الفعلية عند توفرها: «متاح للخياطة» تعرض «في انتظار الخياطة»، و«قيد التنفيذ» تعرض «قيد الخياطة»، واكتمال الخياطة مع بقاء حالة طلب قديمة يعرض «ما بعد الخياطة». يضم المجمع أيضاً حالات التشطيب والمكواة والطباعة والتكييس والفرز والتسليم؛ وبذلك تتوزع الطلبات الحالية على فئات لا تتداخل ولا تبقى «تم القص» ضمن عداد أو شارة الخياطة بعد بدء المرحلة. الإشعارات التشغيلية لغير الإدارة تقتصر على الطلبات الظاهرة للحساب، وتُبسّط للعميل دون أسماء منفذي التعديل أو تفاصيل مالية؛ تفاصيل الإدارة تعرض الحقول التي تغيرت فقط.
- يجب ألا يُمنح أحد دور `admin` من نموذج التسجيل؛ إنشاء أدمن إضافي وترقيته يتمان من إدارة موثوقة في Supabase.

## بيانات التشغيل السحابية

- `orders` يخزن ملف العميل والموديل أو رقمه واسم مرسل القصة والألوان والمقاسات والعدد الأصلي المطلوب (`original_total_pieces`) والعدد الفعلي بعد القص والكمية المسلّمة وحالة الإنتاج وتاريخ التسليم المتوقع ورابطَي الصورة ومصاريف التشغيل الإضافية. تُحفظ الكمية الأصلية عند إنشاء الطلب ولا تتغير عند اعتماد عدد القص؛ وتُهيأ السجلات القديمة بأقرب قيمة متاحة وقت الترحيل، كما يُضبط العدد الأصلي إلى عدد القص إذا لم يكن قد أُدخل قبل بدء القص. تُضاف مصروفات التشغيل مرة واحدة إلى إجمالي حساب الطلب: ضمن المتوقع قبل أول تسليم، ثم ضمن المستحق الفعلي عند تسجيل أول تسليم. حالات الموديل موحدة بهذا الترتيب: «قيد الانتظار»، «قيد الفرش»، «تم الفرش»، «جاهز للقص»، «تم القص»، «جاري الخياطة»، «مكتمل»، «جاهز للتسليم»، «تم التسليم». يحدّث تدفق القص الحالة حتى اعتماد جاهزية القص (`mark_factory_cutting_ready`) وتسجيل العدد النهائي (`finish_factory_cutting`)؛ ولا يتيح أي حقول مالية لمشرف القص. تُسجل كل دفعة تسليم مستقلة باسم المستلم وتاريخها عبر `record_factory_delivery`؛ يظل «مكتمل» متاحاً للتسليم، وتتحول الحالة إلى «تم التسليم» بعد الإغلاق. بعد التسليم لا يمكن تغيير الحالة أو تسجيل دفعات جديدة، لكن يحق للأدمن تصحيح بيانات الموديل والدفعات؛ وتتحدث مبالغ الطلب ورصيد العميل آلياً.
- يمكن للإدارة إضافة صورتين كحد أقصى لكل موديل، ومعاينة كل صورة أو تبديلها أو حذفها بشكل مستقل. تُرفع الصور إلى مخزن Supabase Storage العام `factory-model-images` حتى 25 ميجابايت للصورة؛ وتُعرض صور الموديل كاملة دون قص في بطاقات الموديلات وصفحات العامل والعميل.
- يقرأ العميل طلباته المرتبطة بـ`client_id` فقط عبر `read_factory_orders_client` المقيدة بالحساب المصادق؛ تعرض بوابته حالة الإنتاج والسعر وقيمة المسلّم والمدفوع والمتبقي، إضافة إلى الرصيد السابق المرحّل. لا تُمنح أدوار المصنع الأخرى صلاحية قراءة الأعمدة المالية، ولا تستخدم قراءة `select('*')` للواجهة.

- `production_stages` يخزن مراحل القص والخياطة والتشطيب والتسليم، بما فيها الكمية المستهدفة والمنفذة، وبيانات القماش والتوب والراقات ومصدر الخامة الخارجية والملاحظات الفنية للقص. تظل حالات المراحل التشغيلية منفصلة عن حالة الموديل الموحدة؛ تتيح القصة المعتمدة مشرف الخياطة للبدء، ثم يبدأ تحديث مرحلة الخياطة عند استلامها. بعد اعتماد جاهزية القص، يستخدم إنهاء القص بيانات القماش والسحب المحفوظة في المرحلة ولا يطلب اختياراً جديداً أو يخصم المخزون مرة ثانية.
- قماش الإدارة في `factory_fabrics.stock_scope = 'owner'` ظاهر للأدمن فقط، ويُدار من تبويب «قماش الإدارة». أما تبويب «القماش الداخل» فيظهر للأدمن ومشرف القص: يختار المستخدم نوعاً مسجلاً أو يضيف نوعاً جديداً، ثم يضيف ألوانه وكمياتها، ويمكنه تسجيل أنواع متعددة في الحركة نفسها، ويختار العميل أو يتركه «غير معروف». سحب القماش الخارج يتم عبر القصات فقط ويُخصم آلياً؛ لا يوجد صرف مخزون يدوي من الواجهة. يستطيع الأدمن تعديل أصناف القماش وحذفها؛ يحذف ذلك السجل وحركاته غير المرتبطة بقصة قص، بينما تُحمى الأصناف المستخدمة بقصة أو مرحلة إنتاج. وحدات القياس المعتمدة هي المتر و«توب»؛ «ريب» اسم خامة وليس وحدة قياس. يستطيع الأدمن تعيين العميل لاحقاً.
- `factory_cash_transactions` هو سجل حركة الخزينة، ويحتفظ بالإيرادات والمصروفات ضمن قسم المصاريف في حسابات العملاء؛ تظهر دفعات العملاء تلقائياً كمقبوضات دون تكرارها كإيراد يدوي. يستطيع الأدمن تعديل أو حذف الحركات اليدوية غير المرتبطة بمصاريف موديل؛ تُعدّل مصاريف تشغيل الموديل من محرر الطلب، وتظل حركات الفترات التي تمت تصفيتها غير قابلة للتعديل أو الحذف أو الإضافة بأثر رجعي. يمكن للأدمن تسجيل مصروف أو عهدة على حساب عميل فيظهر في سجل الخزينة وكشف العميل ورصيده، ويقرأ العميل حركات حسابه فقط عبر `read_factory_client_cash_transactions`.
- `factory_order_expenses` يسجل كل مصروف مضاف للموديل كبند مستقل مع البيان والقيمة والتاريخ؛ تُحوّل المصروفات القديمة إلى بند افتتاحي مجمّع مرة واحدة. تضيف دالة `admin_add_factory_order_expense` إلى الإجمالي المالي الموجود وتحدّث سجل الخزينة دون استبدال البنود السابقة، ولا تسمح القراءة إلا للأدمن. لكل عميل حرف كود فريد يُولد عند الإنشاء إن لم يُدخل؛ ويخصص `orders.model_serial` تسلسلاً عالمياً متزايداً، ويُشتق «كود الموديل بالنظام» من حرف العميل والتسلسل. تعتمد واجهة الموديل على كود النظام التلقائي وكود/رقم الموديل للعميل فقط؛ وتحوّل الأكواد القديمة المسجلة في قصص القص إلى حقل كود العميل عند اعتماد القصة.
- معاينات ملخص العميل تعرض اسم ورقم الموديل والكمية والمقاسات والألوان والحالة داخل نوافذ منبثقة، كما تعرض تفاصيل الموديل للقراءة دون فتح شاشة التحرير؛ يظل تعديل الطلبية للأدمن فقط. تتاح طباعة فاتورة موديل من التفاصيل، أو طباعة موديلات مختارة، أو كشف حساب A4 نظيف يتضمن الموديلات والدفعات ومصاريف التشغيل وحركة الحساب. تشمل فئات الحالة الموحدة «قبل القص» و«في انتظار الخياطة» و«قيد الخياطة / جاري الخياطة» و«ما بعد الخياطة»، إلى جانب الموديلات غير المسعّرة أو غير المحصورة. يدخل غير المسلّم في صافي الرصيد المتوقع بعد طرح المدفوع من الرصيد المرحّل والمستحقات ومصاريف التشغيل؛ لذلك يستهلك الفائض قيمة البضاعة المعلقة قبل ظهوره كرصيد دائن. يمكن للأدمن حذف أي طلب غير مؤرشف حتى بعد التسليم؛ تحذف `delete_factory_order` دفعات التسليم ومصروفات التشغيل وحركات القماش المرتبطة، وتعكس أثرها على حساب العميل والخزينة والمخزون. تُحمى الطلبات المؤرشفة ضمن تصفية مالية من الحذف للحفاظ على سجل التسوية.
- شاشة مشرف القص تعرض «طلبات الإدارة» و«قصة جديدة» و«القماش الداخل» و«متابعة الحساب والراتب». يتيح تبويب القص في لوحة الإدارة عرضاً قابلاً للتوسيع بتفاصيل القصة كاملة، وتبويب «إضافة قصة جديدة» يستخدم نموذج القص نفسه. لا تنشئ القصة موديل إنتاج أو تخصم القماش قبل اعتمادها. يختار الأدمن «تأكيد وإضافة للموديلات» أو «تأكيد وإرسال للخياطة»؛ في الحالتين تُنشأ الطلبية ويُخصم القماش ذرياً، وتبقى بيانات القصة محفوظة. ويمكن للإدارة إدخال أي طلب مكتمل القص للخياطة. تُعرض المقاسات المكررة بالترتيب وكل ظهور له عدد مستقل محسوب؛ كما تُعرض الرقات والأتواب والمورد والملاحظات. عند إنهاء القص يمكن تسجيل اسم منفذه. تظهر وحدات المخزون المسجلة كما هي (متر أو توب) ولا يمكن تحويلها دون معامل تحويل.
- تتيح بوابة العميل إرسال طلب قصة / موديل جديد مع صورة وعدد وملاحظات اختيارية بالكامل. تحفظ الطلبات في `factory_client_model_requests` بصورة منفصلة عن أوامر الإنتاج والمخزون والحسابات، وتظهر للإدارة للمراجعة؛ لا تُقبل إلا من حساب عميل نشط مرتبط بملف عميل، وتُقيّد قراءة الطلبات بسياسات RLS للعميل صاحبها والأدمن.

- بطاقات الموديلات والقص والخياطة تعرض ملخصاً قصيراً للصورة والاسم والكمية والألوان والمقاسات، وتفتح «التفاصيل» نافذة مستقلة بالبيانات التشغيلية كاملة. تُجرى تعديلات القص والخياطة في نافذة تحرير منفصلة؛ تعديل كمية وتعليمات الخياطة محمي بدالة `update_factory_sewing_details` للأدمن ومشرف الخياطة، ويتطلب تشغيل أحدث `supabase/schema.sql`.

- تعرض صفحات الدخول وصفحات العامل والقص والخياطة والعميل تنويه أن الموقع تحت الإنشاء، بينما تُستثنى لوحة الإدارة. يظهر نص «مطور الموقع: ZERO» مع صورة رمزية أحادية اللون وأيقونة كود؛ يظهر تذييل الدخول أسفل الصفحة وتظهر بيانات المطور داخل القائمة الجانبية مباشرة تحت زر تسجيل الخروج. الكارت كله رابط واتساب مباشر، ولا يُعرض رقم الهاتف كنص. تتيح لوحة العامل متابعة مهامه وسجلات حضوره وغيابه وسلفه ومصروفاته ومرتبه المرتبطة بحسابه فقط. يحدد الأدمن تخصص العامل (مثل الخياطة أو القص أو الإمبلاج) ويفعّل له صراحةً «إتاحة تسليم طلبية / إنتاج». نموذج التسليم يستخدم عجلة ألوان وواجهة تشبع وسطوع مخصصتين، ويقبل اسم الموديل أو رقمه (يكفي أحدهما)؛ يختار العامل درجات الألوان دون إدخال أسمائها، ويحدد مقاساً وعدداً موجباً لكل توزيع، مع إرفاق صورة إلزامية. يحسب الإجمالي تلقائياً من خانات التوزيع، والملاحظات غير مطلوبة. يعرض سجل العامل معاينات الصور ويمكن إرسال دفعات تابعة مرتبطة بأي تسليم سابق له، سواء كان معتمداً أو مرفوضاً. تظهر علامة التسليم التابع في لوحة الإدارة، حيث يمكن اعتماد الطلب أو رفضه أو حذف الطلبات غير المعتمدة وغير المرتبطة بتسليمات تابعة؛ وتُضاف الإنتاجات المعتمدة إلى `factory_finished_goods` لتظهر للعميل المالك فقط. صور التسليم تحفظ في مخزن `factory-model-images` ضمن مجلد خاص بالعامل، ولا تمنح صلاحية العامل وصولاً إلى مخزون العميل أو اعتماد التسليم. شغّل `supabase/schema.sql` كاملاً لترحيل حقول ربط التسليمات التابعة وتفعيل قيود الصور والألوان والكميات وسياسات RLS ودالة الاعتماد.

- يتيح سجل النقدية حذف حركة الإيراد/المصروف المسجلة يدوياً بواسطة `delete_factory_cash_transaction`. يمكن حذف حركة مخزون غير مرتبطة بأمر قص بواسطة `delete_factory_fabric_transaction`؛ يعكس الإجراء أثر الحركة على الرصيد ويرفض الحذف إذا أدى إلى رصيد سالب. تبقى حركات القماش المرتبطة بأمر قص محمية للحفاظ على تطابق سجل الإنتاج والمخزون.
- لا تُرحّل السجلات القديمة من `localStorage` تلقائيًا؛ تظل محفوظة على أجهزتها القديمة لكن لا تظهر في اللوحات بعد التحويل إلى التخزين السحابي، لذا انقل ما يلزم يدوياً قبل الاعتماد على النسخة الجديدة.
- يلزم تشغيل `supabase/schema.sql` كاملاً لتحديث `orders` و`production_stages` و`factory_deliveries` و`factory_fabrics` و`factory_fabric_transactions` و`factory_live_signals` و`factory_auth_events` وسياسات RLS والنشر. يوحّد ترحيل المخزون القيم القديمة إلى وحدة «توب»، ويعرض التطبيق الاسم الموحد فقط. في القص، لا يقبل المخزون إلا كمية صحيحة بوحدة «توب»، بينما تقبل الخامة الخارجية وحدة «متر» فقط. تحفظ الطلبية طبيعة الشغل وتوزيع العدد على الألوان والمقاسات. تبث الطلبات والمراحل إشارات آمنة، وتُبث تعديلات الحسابات والتسليمات والسجلات والمخزون وتسجيلات الدخول؛ وتعاد قراءة البيانات بصلاحيات الدور دون كشف جداول مالية. يسجل `auth.js` أحداث الدخول والتسجيل الصريحة في `factory_auth_events`، بينما تحديث بيانات الدور والحالة يصل عبر `users`. إذا كان نشر `supabase_realtime` شاملاً لكل مخطط `public`، يصدر المخطط تحذيراً؛ استخدم نشر الجداول المحددة لحماية خصوصية الأعمدة المالية. حالات التشغيل هي «قيد الفرش»، «تم الفرش / جاهز للقص»، «تم القص»، «في انتظار الخياطة»، ثم «جاري الخياطة» بعد استلام مشرف الخياطة.
- تحفظ جداول `users`, `factory_clients`, `orders`, و`production_stages` الحقول المنظمة بقيودها؛ يحمل `orders` اسم الموديل ورقمه مباشرة، بينما تتسع سجلات الدفعات والمهام وأذونات الانصراف عبر JSONB.
- نموذج الطلبية يربط العميل بملفّه ويعرض اسم العميل والبراند دون رقم الهاتف، ويحدد أقسام التشغيل المطلوبة بعلامات الاختيار، مع إبقاء نوع المقاسات اختيارياً وتوزيع العدد على الألوان والمقاسات في `orders.color_size_distribution`. يمكن إدخال العدد الكلي أو الأعداد لكل مقاس؛ تُراجع قاعدة البيانات أن مجموع التوزيع يطابق العدد المسجل. عند إضافة طلب بحالة «تم التسليم» يظهر حقل العدد المسلّم، ويسجله `save_factory_order` كدفعة تاريخية حتى تتطابق التسليمات والماليات؛ أما التسليمات اللاحقة فتُسجل من مسارها المستقل.
- بيانات الاتصال محصورة في تبويب ملفات العملاء/حسابات العملاء؛ جداول الطلبات وإدارة المستخدمين لا تعرض أرقام الهاتف. في نموذج الموديل يختار المستخدم العميل أو البراند من قائمتين منفصلتين ومتبادلتين. يمكن تحديد أقسام القص والخياطة والتشطيب والمكوى والأمبلاج والتكييس، وتسعير القطعة كسعر إجمالي أو بجمع السعر المستقل لكل قسم. تحفظ الأقسام وطريقة التسعير وتفاصيل أسعار الأقسام في `orders.work_stages`, `orders.pricing_mode`, و`orders.stage_prices`؛ ويظل سعر القطعة الإجمالي هو أساس حسابات التسليم والرصيد.

## ملفات المشروع

- `index.html`: تسجيل الدخول وإنشاء الحساب، وصفحة البداية الافتراضية على GitHub Pages.
- `dashboards/`: لوحات الإدارة والقص والخياطة والعامل والعميل.
- `js/auth.js`: المصادقة، إرسال طلبات الحساب، وتوجيه المستخدم حسب حالته ودوره.
- `js/dashboard.js`: عرض اللوحات وإدارة تفعيل الحسابات وأوامر التشغيل ومراحل القص والخياطة والسجلات المرنة عبر Supabase.
- `js/supabase-config.js`: عنوان المشروع ومفتاح النشر العام.
- `supabase/schema.sql`: الجداول الأساسية ومخزن السجلات المرن JSONB والحسابات المرتبطة بـAuth وسياسات RLS والدوال.
- `css/styles.css`: التنسيق ودعم الشاشات الصغيرة.

## ملاحظات تشغيل

- يضم ملف العامل تبويبي «المستحقات والماليات» و«البيانات الشخصية»، ويعرض الأجر اليومي والساعة وحركة الحساب الشهرية. الغياب بدون إذن لا يحتسب يومه ضمن الأجر ويُسجل عليه خصم يوم عمل واحد؛ ويمكن للأدمن إلغاء أي خصم مسجل من سجل العامل أو سجل المخالفات، لتُعاد حسابات المستحقات بعد الحذف.
- قراءة `orders` محكومة بسياسات RLS حسب الدور وملكية العميل؛ لا تمنح `SELECT` عاماً لكل الحسابات المسجلة. صلاحيات الأعمدة تشمل أكواد الموديل التي تحتاجها لوحات القص والخياطة، بينما لا تجلب لوحة العامل الطلبات غير اللازمة لها. عند تعذر قراءة الطلبات للمشرفين، تعرض اللوحة تنبيهاً واضحاً وتبقي بقية الأقسام متاحة. بعد تحديث صلاحيات قاعدة البيانات شغّل `supabase/schema.sql` كاملاً في SQL Editor.
- تأكد من تعطيل **Confirm email** قبل التسجيل باسم مستخدم، كي يصدر Supabase Auth جلسة تسمح بإدراج الصف بأمان. شغّل `supabase/schema.sql` لتفعيل سياسة RLS ومنح صلاحية إدراج الأعمدة المسموحة؛ لا يحتاج هذا المسار إلى trigger.
- كلمات المرور تُدار بواسطة Supabase Auth ولا تُحفظ في جدول `users` أو في ملفات الواجهة.
- لا تصبح طلبات التسجيل والتفعيل مشتركة بين الأجهزة حتى تشغيل SQL وإعداد حساب الأدمن وإعداد البريد ونشر المشروع.
- تعرض لوحة مشرف الخياطة القصّات المتاحة للبدء مع قائمة متابعة شخصية للقراءة فقط. تعرض حسابات العمال والمشرفين الأجر اليومي والساعة والمستحقات والسلف والخصومات وسجل التصفية الخاص بالحساب، وتقتصر بيانات شؤون العاملين على الملف المرتبط بالحساب النشط عبر سياسة RLS.
- تتبع عدادات الموديلات في ملفات العملاء ترتيب الحالات الديناميكي لكل طلب، بما في ذلك «في انتظار الخياطة» ومراحل التشغيل المخصصة. تقتصر تفاصيل مشرف الخياطة على بيانات الموديل والأعداد والمقاسات والألوان وسجل القصات، دون حقول الفرش والخامات أو أزرار تعديل بيانات الإنتاج؛ يظل إجراء نقل مرحلة الخياطة متاحًا.
- عند تشغيل `supabase/schema.sql` تُنشأ ملفات مالية تلقائياً للحسابات النشطة أو الموقوفة ذات أدوار العامل أو مشرف القص أو مشرف الخياطة، وتُزامن حسابات الموظفين الجدد أو التي يُعتمد دورها لاحقاً. تظهر الملفات في شؤون العمال ويمكن للإدارة إعداد الأجر والمعاملات المالية لها؛ الحسابات المعلقة والعملاء والأدمن لا تُعامل كملفات موظفين تلقائياً.
- يتيح حساب العميل إضافة خصم تسوية مثل تنزيل الكسور أو الخصم التشغيلي، ويُخصم من الرصيد الحالي ويظهر في كشف الحساب والترحيل عند التصفية، دون تسجيل أي حركة نقدية في الخزنة. شغّل `supabase/schema.sql` لتفعيل الدالة وسياسات القراءة اللازمة.
- يعرض مخزون القماش عدد الأثواب والأمتار في عمودين وإجماليين منفصلين، ويظهر مالك القماش لكل صنف. يحتوي ملف العميل على ملخص رصيد القماش المتاح حسب النوع واللون مع فصل الوحدات.
- إشعارات التحديث تعرض «تحديث جديد في البرنامج» ووقت التحديث فقط، دون أسماء العملاء أو الموديلات أو تفاصيلها؛ تظهر قائمة المتصلين في لوحة الإدارة فقط. شغّل `supabase/schema.sql` المحدّث لتفعيل XS والمقاسات المتكررة وحفظ اسم منفذ القص.
- تُعرض تفاصيل القص المحفوظة (مسؤول القص، الخامة ومصدرها وتفاصيل المورد، الأتواب، المقاسات والراقات) في لوحة الإدارة وبوابة العميل ونموذج التسعير. تُنقل تفاصيل المورد عند اعتماد القصة، وتعديل الإدارة يستخدم دالة مستقلة لتسوية سحب المخزون دون تكراره مع الحفاظ على حالة الطلب وبيانات القص عند تحديث بيانات السعر.
- حالات الإنتاج تنتقل بعد إكمال الخياطة تلقائياً إلى أول مرحلة إضافية مختارة (التشطيب أو المكواة أو الطباعة أو التكييس/الأمبلاج أو الفرز)، وتفعّل المرحلة التالية بعد اكتمال كل مرحلة. بعد آخر مرحلة، تصبح الحالة «جاهز للتسليم»، ثم «تم التسليم» عبر إجراء التسليم. يمكن للإدارة تحديث المراحل الإضافية؛ يلزم تشغيل `supabase/schema.sql` لتفعيل سير العمل.
- تتيح بطاقة الموديل في لوحة الإدارة إدخاله للخياطة بعد اكتمال القص؛ ويتحقق إجراء قاعدة البيانات من اكتمال مرحلة القص قبل إتاحة الطلب للمشرف. تعرض شاشة الخياطة المقاسات المكررة والألوان والخامات والراقات والتعليمات في بطاقات تفصيلية، وتُعرض أسماء الألوان دون أكواد HEX.
- تعرض الإدارة تبويبات القصات النشطة وسجل القصات وإضافة قصة جديدة. تنتقل الأوامر إلى السجل عند إتاحتها للخياطة، وتظهر بحالة «في انتظار الخياطة» حتى يبدأ مشرف الخياطة العمل. اختُصرت بطاقات القص والخياطة، وأصبحت التفاصيل التشغيلية الكاملة تفتح في نافذة مستقلة غير مالية.
- تعرض بطاقات القص والخياطة المقاسات وأعدادها في كبسولات منفصلة، وتجمع بطاقة الخياطة الصورة وبيانات الموديل والألوان والمقاسات والإجمالي وأزرار الإجراءات أفقياً. يمكن للأدمن بدء الخياطة وإنهاؤها من قسمها؛ عند الإنهاء تتحدث الحالة تلقائياً إلى المرحلة الإضافية التالية المختارة أو «جاهز للتسليم»، وتُحدّث العدادات بعد إعادة تحميل البيانات. تتكيف معاينة الصورة المكبرة مع أبعاد الصورة وارتفاع الشاشة دون خلفية داخلية داكنة.
- يتيح نموذج تعديل الطلبية للأدمن تعديل بيانات القصة والخامات والأتواب والراقات من نفس النافذة، مع حفظ ترتيب المقاسات المكررة كما هو. تؤجل تحديثات Realtime إعادة رسم اللوحة ما دام نموذج أو نافذة حوار مفتوحاً أو نموذج ظاهر تغيّرت بياناته، ثم تُستأنف بعد الحفظ أو الإغلاق اليدوي.
- صور القطع قابلة للفتح في معاينة مكبرة من بطاقات الموديلات والقص والخياطة وملفات العملاء. تسجّل المصروفات الخارجية كحركات خزنة منفصلة، مع تحديد ما إذا كان المصروف مستحقاً على العميل أو تشغيلياً على المصنع أو مدمجاً في سعر القطعة؛ لا تضاف الأنواع غير المستحقة على حساب العميل إلى مديونيته. شغّل `supabase/schema.sql` المحدّث لتطبيق أنواع المصروفات وحركات الخزنة المرتبطة بها.
