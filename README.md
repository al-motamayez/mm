# AL-MOTAMAYEZ

واجهة عربية لإدارة مصنع الملابس، مع مصادقة وطلبات حسابات وأوامر تشغيل ومراحل إنتاج وسجلات مرنة مشتركة بين الأجهزة عبر Supabase.

## إعداد Supabase

1. افتح SQL Editor في مشروع Supabase وشغّل الملف كاملًا `supabase/schema.sql`؛ ينشئ جداول `users`, `factory_clients`, `orders`, `production_stages`, `factory_records`, `factory_fabrics`, `factory_fabric_transactions` و`factory_cash_transactions` والسياسات والدوال المطلوبة، فلا يلزم إنشاؤها يدوياً جدولاً جدولاً. اسم الموديل ورقمه محفوظان مباشرة في كل طلبية ولا يعتمد النظام على جدول موديلات منفصل.
   إذا وجد جدول `users` القديم الذي يحتوي كلمة مرور نصية، يحفظ السكربت حقول الملف الشخصي غير الحساسة في `users_legacy_profiles` بعد حذف عمود كلمة المرور، ثم يربط الملفات التي لها حساب Auth مطابق. تبقى الملفات غير المرتبطة في الأرشيف الخاص، ولا تُنقل أي كلمة مرور إلى النظام الجديد. احتفظ بنسخة احتياطية قبل تشغيل ترحيل بنيوي على قاعدة الإنتاج.
2. من **Authentication → Providers → Email** عطّل **Confirm email**. نموذج التسجيل لا يجمع بريدًا إلكترونيًا، لذلك يستخدم النظام عنوانًا داخليًا ثابت النطاق مشتقًا من اسم المستخدم؛ لا يمكن تأكيده برسالة بريد.
3. من **Authentication → Users** تأكد من وجود مستخدم الأدمن مع تفعيل **Auto confirm user**:
   - البريد: `mohamed01007033454@gmail.com` (يدعم النظام أيضاً العنوان الداخلي القديم `zero0@accounts.al-motamayez.invalid`)
   - عيّن كلمة المرور المطلوبة من المالك مباشرةً في لوحة Supabase، ولا تحفظها في ملفات المشروع.
4. أعد تشغيل `supabase/schema.sql` لإضافة/ترقية ملف الحساب المرتبط بهذا المستخدم تلقائيًا إلى `admin` و`active`. يجب أن يكون مستخدم Auth موجودًا مسبقًا؛ المخطط لا ينشئ حساب مصادقة أو كلمة مرور. بعد المصادقة، يمكن لحساب الأدمن المؤكد فقط استعادة ملفه عبر `ensure_factory_admin_profile` إذا كان مفقودًا، دون تعطيل RLS.
5. أكمِل إنشاء الأدمن وترقيته قبل نشر الواجهة. انشر مجلد المشروع عبر خادم صفحات ثابتة أو استضافة HTTPS وافتح `login.html`. لا تستخدم `file://` لتشغيل طلبات Supabase.

وجود صف `ZERO0` في `public.users` وحده لا ينشئ مستخدمًا في Supabase Auth ولا يسمح بتسجيل الدخول. يجب وجود مستخدم Auth بالبريد المرتبط بالأدمن وأن يشير `public.users.id` إلى معرّف مستخدم Auth نفسه. لا تحاول مقارنة كلمة المرور من المتصفح أو تخزينها في `public.users`.

يستخدم `js/supabase-config.js` عنوان المشروع ومفتاح النشر العام (publishable key). المفتاح العام مخصص للواجهة؛ لا تضع `service_role` أو أي مفتاح سري في ملفات المشروع. لا تنشئ الواجهة جداول أو أعمدة SQL تلقائياً؛ أي تغيير مستقبلي في الحقول المرنة يحفظ كقيمة JSONB داخل `factory_records.payload` ولا يحتاج عموداً جديداً. تبقى الجداول العلائقية الأساسية ثابتة ومقيدة، ويتطلب تغيير بنيتها ترحيلاً مقصوداً. إبقاء RLS مفعّلاً ضروري لمنع الزوار من قراءة أو تعديل حسابات المصنع.

## الحسابات والصلاحيات

- الدخول باسم المستخدم وكلمة المرور. يحول العميل اسم المستخدم إلى عنوان Auth داخلي؛ رقم الهاتف مطلوب عند التسجيل ويحفظ كبيانات ملف شخصي فقط، ولا يرسل النظام SMS.
- تحفظ جلسة Supabase تلقائيًا في `localStorage` مع تحديث رمز الجلسة؛ خيار «البقاء مسجلاً للدخول» في صفحة الدخول يحفظ الجلسة في هذا الجهاز، وإلغاء اختياره يحفظها في `sessionStorage` حتى إغلاق جلسة المتصفح. إذا بقيت الجلسة صالحة، يعيد فتح صفحة الدخول توجيه المستخدم إلى لوحته تلقائيًا.
- يمكن للأدمن تسجيل الدخول باسم `ZERO0` أو ببريده المسجل في Supabase Auth؛ يحول النموذج `ZERO0` إلى `mohamed01007033454@gmail.com`، ويعطي النظام هذا البريد أولوية على اسم المستخدم الوصفي في Auth metadata. يجب أن تكون كلمة المرور هي كلمة مرور Supabase Auth، وأن يطابق `users.id` معرّف حساب Auth؛ صف users وحده لا يصادق الدخول.
- تتيح صفحة الدخول طلب رابط إعادة تعيين كلمة المرور إلى بريد Auth، ثم حفظ كلمة مرور جديدة بعد فتح الرابط. يجب إضافة عنوان صفحة الدخول المنشورة (والمحلي عند التطوير) إلى قائمة Redirect URLs المسموح بها في Supabase Auth.
- التسجيل ينشئ مستخدم Auth ثم يضيف الواجهة صفًا معلقًا إلى `users` مباشرةً، ولا يعتمد على trigger؛ تقيد سياسة RLS الإضافة بصف المستخدم الحالي مع `role = null` و`status = 'pending'`. عند إعادة المحاولة بعد إنشاء Auth وفشل إضافة الصف، يتحقق النظام من بيانات Auth ثم يستكمل الصف الناقص دون تكرار الحساب. ويقبل أيضاً صفاً أنشأه trigger مسبقاً. تعرض لوحة الإدارة الطلبات من الجدول نفسه، سواء كان التعليق ممثلاً بـ`status = 'pending'` أو `role = 'pending'`.
- جدول `users` يحفظ الاسم واسم المستخدم والبريد ورقم الهاتف والدور والحالة؛ البريد يُزامن مع حساب Supabase Auth، وكلمات المرور تبقى في Auth ولا تُخزّن أو تُرسل ضمن بيانات المستخدم الوصفية أو تعرض في لوحة الإدارة.
- الأدمن يقرأ الطلبات المعلقة من جدول `users` ويختار الدور ويفعّله. سياسات RLS تمنع المستخدم من تغيير دوره أو حالته بنفسه.
- يمكن للأدمن تعليق حساب نشط وإعادة تفعيله من جدول المستخدمين. تفحص صفحة الدخول الحالة وتمنع التوجيه للحساب المعلق، كما تمنع سياسات قاعدة البيانات صلاحيات الأدوار للحساب الموقوف.
- حذف المستخدم من لوحة الإدارة يستدعي `public.delete_user_by_admin(target_user_id)`؛ تتحقق الدالة من صلاحية الأدمن النشط وتحمي حسابات الإدارة، بينما لا يُمنح العميل صلاحية حذف مباشرة من `public.users`. يحذف الإجراء صف الملف الشخصي فقط ولا يحذف حساب Supabase Auth. قيد `orders.client_id` مضبوط على `ON DELETE SET NULL` حتى تبقى الطلبات والتسليمات محفوظة عند حذف ملف المستخدم؛ يعيد ترحيل المخطط ضبط القيود القديمة على هذا العمود.
- يمكن حذف ملف العميل من بطاقة العميل أو قائمة الملفات عبر `public.delete_factory_client(requested_client_id)` بعد حذف صف حساب الدخول المرتبط إن وجد؛ ترفض الدالة حذف الملفات التي لها طلبات أو تسليمات أو حركات مالية أو مخزون، حفاظاً على سجل التشغيل والحساب.
- زر مسح النظام موجود ضمن قسم «طلبات مستخدمي النظام» ويستدعي `public.reset_factory_data()` كعملية ذرّية بصلاحية أدمن. تمسح الدالة سجلات التشغيل والمخزون والحسابات والحركات وتحذف حسابات Supabase Auth الأخرى مع إبقاء حساب الأدمن الحالي؛ تُحذف صور الموديلات بعدها عبر Supabase Storage API، وفق سياسة حذف للأدمن فقط. شغّل المخطط لتفعيل الدالة والسياسة.
- تستخدم صفحات الدخول ولوحات التحكم نوافذ تأكيد وإشعارات مخصصة من `js/ui.js` بدل نوافذ المتصفح الافتراضية.
- لوحة الإدارة تعرض كل قسم في القائمة الجانبية، ويحتوي قسم «الموديلات والطلبيات» على تبويبين داخليين: قائمة الموديلات وإدارة حالاتها. يجمع قسم «إدارة العملاء» الحسابات وملفات العملاء بتبويبين، وتعرض بطاقات الملخص الحالات ومعاينات قابلة للفتح؛ يمكن تعديل بيانات المحل والتواصل من الملف دون إنشاء حساب دخول تلقائياً. تعرض لوحة التحكم النقدية الحالية في الدرج، ومديونيات العملاء عن البضاعة المسلّمة، وقيمة البضاعة التي لم تُسلّم بعد؛ وتتحدث المؤشرات مع أحداث Realtime للمدفوعات والتسليمات والحركات النقدية. لا يغيّر تقدم القص حالة الطلب تلقائياً.
- يجب ألا يُمنح أحد دور `admin` من نموذج التسجيل؛ إنشاء أدمن إضافي وترقيته يتمان من إدارة موثوقة في Supabase.

## بيانات التشغيل السحابية

- `orders` يخزن ملف العميل والموديل أو رقمه واسم مرسل القصة والألوان والمقاسات والعدد الأصلي المطلوب (`original_total_pieces`) والعدد الفعلي بعد القص والكمية المسلّمة وحالة الإنتاج وتاريخ التسليم المتوقع ورابط الصورة ومصاريف التشغيل الإضافية. تُحفظ الكمية الأصلية عند إنشاء الطلب ولا تتغير عند اعتماد عدد القص؛ وتُهيأ السجلات القديمة بأقرب قيمة متاحة وقت الترحيل، كما يُضبط العدد الأصلي إلى عدد القص إذا لم يكن قد أُدخل قبل بدء القص. تُضاف مصروفات التشغيل مرة واحدة إلى إجمالي حساب الطلب: ضمن المتوقع قبل أول تسليم، ثم ضمن المستحق الفعلي عند تسجيل أول تسليم. يبدأ عمل مشرف القص بحالة «قيد الفرش»، وتسمح دالتا `update_factory_cutting_progress` و`mark_factory_cutting_ready` بحفظ الراقات تدريجيًا واعتماد الفرشة قبل تسجيل العدد النهائي بواسطة `finish_factory_cutting`، دون إتاحة أي حقول مالية للمشرف. ينتقل الطلب بعد القص إلى «تم القص»، ثم يغيّر الأدمن حالته إلى «معلق - في انتظار الخياطة» وعند بدء الخياطة فعليًا إلى «في الخياطة». يختار مشرف القص ملف العميل من قائمة آمنة ويُربط الطلب به فور الحفظ؛ فتظهر الطلبية في سجل العميل وبوابته عند ارتباط ملفه بحساب دخول. تسجل دالة `record_factory_delivery` كل دفعة مستقلة باسم المستلم وتاريخها، وتعرض تفاصيل الموديل سجل الدفعات وإجماليها. زر التسوية يتيح بعد دفعات سابقة الإغلاق على المسلّم أو تسليم كامل المتبقي، وعند عدم وجود دفعات يتيح تسليم العدد كاملاً أو تسجيل دفعة أولى جزئية؛ ثم يحوّل الطلب إلى «تم التسليم» دون أرشفته، ليظل ظاهراً ضمن كشف الحساب. يُعاد حساب المبالغ تلقائياً من الدفعات والسعر الحالي. بعد الإغلاق لا يمكن تغيير الحالة أو تسجيل دفعات جديدة، لكن يحق للأدمن تعديل بيانات الموديل والعدد الأصلي والسعر، وتصحيح كمية كل دفعة عبر `admin_update_factory_delivery_quantity`؛ وتتحدث مبالغ الطلب ورصيد العميل آلياً.
- تُرفع صور الموديلات إلى مخزن Supabase Storage العام `factory-model-images` (صور JPG/PNG/WEBP حتى 5 ميجابايت). يسمح المخطط بالرفع للأدمن ومشرف القص فقط، وتظهر الصورة المصغرة في بطاقات الموديلات وبوابة العميل.
- يقرأ العميل طلباته المرتبطة بـ`client_id` فقط عبر `read_factory_orders_client` المقيدة بالحساب المصادق؛ تعرض بوابته حالة الإنتاج والسعر وقيمة المسلّم والمدفوع والمتبقي، إضافة إلى الرصيد السابق المرحّل. لا تُمنح أدوار المصنع الأخرى صلاحية قراءة الأعمدة المالية، ولا تستخدم قراءة `select('*')` للواجهة.
- يعرض تبويب إدارة حالات الموديلات الحالات المقفلة للقراءة فقط. حالة «تم التسليم» (مع الحالات القديمة للطلبات المغلقة) تمنع تغيير حالة الطلب أو تسجيل تسليمات جديدة؛ مع بقاء صلاحية الأدمن لتصحيح بيانات الموديل والدفعات بعد الإغلاق. يمكن للأدمن ضبط كمية دفعة التسليم إلى صفر لإزالتها وإعادة احتساب الإجمالي، ويعود الطلب إلى «جاهز للتسليم» إذا لم تبقَ أي دفعة. يُفرض القفل في الواجهة ودوال قاعدة البيانات وسياسات تحديث مراحل الإنتاج، وتُزامن التعديلات المالية عبر Realtime وإعادة قراءة بيانات الدور الحالي.
- `production_stages` يخزن مراحل القص والخياطة والتشطيب والتسليم، بما فيها الكمية المستهدفة والمنفذة، وبيانات القماش والتوب والراقات ومصدر الخامة الخارجية والملاحظات الفنية للقص. تظل حالة الطلب مستقلة ويغيرها الأدمن يدوياً؛ عند اختيار «في الخياطة» يبدأ تحديث مرحلة الخياطة.
- قماش الإدارة في `factory_fabrics.stock_scope = 'owner'` ظاهر للأدمن فقط، ويُدار من تبويب «قماش الإدارة». أما تبويب «القماش الداخل» فيظهر للأدمن ومشرف القص: يختار المستخدم نوعاً مسجلاً أو يضيف نوعاً جديداً، ثم يضيف ألوانه وكمياتها، ويمكنه تسجيل أنواع متعددة في الحركة نفسها، ويختار العميل أو يتركه «غير معروف». سحب القماش الخارج يتم عبر القصات فقط ويُخصم آلياً؛ لا يوجد صرف مخزون يدوي من الواجهة. يستطيع الأدمن تعديل أصناف القماش وحذفها؛ يحذف ذلك السجل وحركاته غير المرتبطة بقصة قص، بينما تُحمى الأصناف المستخدمة بقصة أو مرحلة إنتاج. وحدات القياس المعتمدة هي المتر و«توب»؛ «ريب» اسم خامة وليس وحدة قياس. يستطيع الأدمن تعيين العميل لاحقاً.
- `factory_cash_transactions` هو سجل حركة الخزينة، ويحتفظ بالإيرادات والمصروفات ضمن قسم المصاريف في حسابات العملاء؛ تظهر دفعات العملاء تلقائياً كمقبوضات دون تكرارها كإيراد يدوي. يستطيع الأدمن تعديل أو حذف الحركات اليدوية غير المرتبطة بمصاريف موديل؛ تُعدّل مصاريف تشغيل الموديل من محرر الطلب، وتظل حركات الفترات التي تمت تصفيتها غير قابلة للتعديل أو الحذف أو الإضافة بأثر رجعي. يمكن للأدمن تسجيل مصروف أو عهدة على حساب عميل فيظهر في سجل الخزينة وكشف العميل ورصيده، ويقرأ العميل حركات حسابه فقط عبر `read_factory_client_cash_transactions`.
- معاينات ملخص العميل تعرض اسم ورقم الموديل والكمية والمقاسات والألوان والحالة داخل نوافذ منبثقة، كما تعرض تفاصيل الموديل للقراءة دون فتح شاشة التحرير؛ يظل تعديل الطلبية للأدمن فقط. تتاح طباعة فاتورة موديل من التفاصيل، أو طباعة موديلات مختارة، أو كشف حساب A4 نظيف يتضمن الموديلات والدفعات ومصاريف التشغيل وحركة الحساب. تشمل فئات مستقلة لـ«تحت الإنشاء» و«قيد التصنيع» والموديلات غير المسعّرة أو غير المحصورة. يُحتسب المطلوب الفعلي من المسلّمات ومصاريف التشغيل، وتظهر قيمة غير المسلّم في التوقعات؛ ويُطرح المدفوع من الرصيد المرحّل والمستحقات والمصروفات المرتبطة. يمكن للأدمن حذف أي طلب غير مؤرشف حتى بعد التسليم؛ تحذف `delete_factory_order` دفعات التسليم ومصروفات التشغيل وحركات القماش المرتبطة، وتعكس أثرها على حساب العميل والخزينة والمخزون. تُحمى الطلبات المؤرشفة ضمن تصفية مالية من الحذف للحفاظ على سجل التسوية.
- شاشة مشرف القص تفصل بين «طلبات الإدارة» و«قصة جديدة» كقسمين مستقلين، وتعرض «القماش الداخل» و«متابعة الحساب والراتب». بعد إتمام الفرش، يسجل المشرف القصة دفعة واحدة باختيار العميل أو البراند (كل منهما مستقل)، والموديل، والقماش والكمية، والمقاسات، والألوان وعدد الراقات. تظهر الوحدات المسجلة للمخزون كما هي (متر أو توب) ولا يمكن تحويلها دون معامل تحويل، بينما تتيح الخامة الخارجية اختيار المتر أو التوب. يحسب النظام العدد النهائي ويحفظ القصة جاهزة للقص بضغطة واحدة، دون حفظ مرحلي أو تحديثات تلقائية أثناء الإدخال. تسجل قاعدة البيانات اسم المشرف المصادق وتربط الطلب بملف العميل وخصم القماش في معاملة واحدة.
- اختيار الألوان يستخدم حقل HTML5 من نوع `color` لقبول أي درجة لونية، مع إمكانية إضافة عدة درجات وإزالتها. في إدخال القص يُحدد المشرف عدد الراقات لكل لون والمقاسات؛ يحسب النظام كمية كل مقاس بجمع الراقات والإجمالي بضربها في عدد المقاسات المختارة، ثم يحفظ بيانات اللون والراقات في `production_stages.color_ply_data`.
- شاشة القص ترتب أوامر الإدارة حسب الأولوية (عاجل، مرتفع، عادي)، وتجمع بيانات الفرشة الفنية: القماش، كمية القماش ووحدتها، وعدد الراقات. تعرض قائمة «متابعة الحساب والراتب» سجلات الحضور والسلف والمرتب المرتبطة بمعرف حساب المشرف فقط، من مجموعات `attendance` و`advances` و`payroll` في `factory_records`.
- أضف ملف العميل أولاً من صفحة العملاء ثم اختره من القائمة عند إنشاء الطلبية. يمكن أن يكون الملف بلا حساب دخول؛ وعند ربطه بحساب عميل نشط يتاح عرض الطلبات في بوابة العميل.
- سياسات RLS تقصر أوامر العميل على حسابه، وتحدّ من عرض المراحل وتعديلها حسب الدور.
- تحفظ الدفعات والمهام وأذونات الانصراف في `factory_records` كسجلات JSONB مرنة؛ يمكن إضافة حقول داخل هذه السجلات دون إنشاء أعمدة جديدة. لا يتحول التخزين إلى إنشاء تلقائي لجداول SQL، ولا تُقبل حقول علائقية جديدة أو تغيير قواعد الصلاحيات دون تحديث مخطط مدروس.
- ترتبط كل دفعة بملف العميل عبر `customerId`؛ تسجل عبر `save_factory_payment` مع حمايتها بعد إقفال الفترة. يمكن حذف دفعة غير مؤرشفة عبر `delete_factory_payment`، مع بقاء الدفعات في الفترات المصفّاة محمية؛ يعاد احتساب الرصيد بعد الحذف. قيمة البضاعة المستحقة بعد التسليم تساوي مجموع الكميات المسلّمة مضروبة في سعر القطعة، والمتبقي يساوي الرصيد السابق المرحّل زائد القيمة الحالية بعد التسليم ناقص الدفعات ودفعات الطلب. تعديل سعر القطعة يعيد احتساب سجلات التسليم المرتبطة والرصيد فورًا. تعرض بطاقة العميل المطلوب بعد التسليم والرصيد المتبقي وتنبيه الموديلات غير المسعّرة، وتعرض «تم السداد بالكامل» عند وصول الرصيد إلى صفر. تجمع صفحة التفاصيل بيانات العميل والطلبات والتسليمات والدفعات والتسويات المؤرشفة في كشف مالي قابل للطباعة أو الحفظ PDF.
- يتيح سجل النقدية حذف حركة الإيراد/المصروف المسجلة يدوياً بواسطة `delete_factory_cash_transaction`. يمكن حذف حركة مخزون غير مرتبطة بأمر قص بواسطة `delete_factory_fabric_transaction`؛ يعكس الإجراء أثر الحركة على الرصيد ويرفض الحذف إذا أدى إلى رصيد سالب. تبقى حركات القماش المرتبطة بأمر قص محمية للحفاظ على تطابق سجل الإنتاج والمخزون.
- لا تُرحّل السجلات القديمة من `localStorage` تلقائيًا؛ تظل محفوظة على أجهزتها القديمة لكن لا تظهر في اللوحات بعد التحويل إلى التخزين السحابي، لذا انقل ما يلزم يدوياً قبل الاعتماد على النسخة الجديدة.
- يلزم تشغيل `supabase/schema.sql` كاملاً لتحديث `orders` و`production_stages` و`factory_deliveries` و`factory_fabrics` و`factory_fabric_transactions` و`factory_live_signals` و`factory_auth_events` وسياسات RLS والنشر. يوحّد ترحيل المخزون القيم القديمة إلى وحدة «توب»، ويعرض التطبيق الاسم الموحد فقط. في القص، لا يقبل المخزون إلا كمية صحيحة بوحدة «توب»، بينما تقبل الخامة الخارجية وحدة «متر» فقط. تحفظ الطلبية طبيعة الشغل وتوزيع العدد على الألوان والمقاسات. تبث الطلبات والمراحل إشارات آمنة، وتُبث تعديلات الحسابات والتسليمات والسجلات والمخزون وتسجيلات الدخول؛ وتعاد قراءة البيانات بصلاحيات الدور دون كشف جداول مالية. يسجل `auth.js` أحداث الدخول والتسجيل الصريحة في `factory_auth_events`، بينما تحديث بيانات الدور والحالة يصل عبر `users`. إذا كان نشر `supabase_realtime` شاملاً لكل مخطط `public`، يصدر المخطط تحذيراً؛ استخدم نشر الجداول المحددة لحماية خصوصية الأعمدة المالية. حالات التشغيل هي «قيد الفرش»، «تم الفرش / جاهز للقص»، «تم القص»، «معلق - في انتظار الخياطة»، ثم «في الخياطة» التي لا يبدأها إلا الأدمن.
- تحفظ جداول `users`, `factory_clients`, `orders`, و`production_stages` الحقول المنظمة بقيودها؛ يحمل `orders` اسم الموديل ورقمه مباشرة، بينما تتسع سجلات الدفعات والمهام وأذونات الانصراف عبر JSONB.
- نموذج الطلبية يربط العميل بملفّه ويعرض اسم العميل والبراند دون رقم الهاتف، ويحفظ طبيعة الشغل (`full_cutting` أو `ready_sewing`) وتوزيع العدد على الألوان والمقاسات في `orders.color_size_distribution`. يمكن إدخال العدد الكلي أو الأعداد لكل مقاس؛ تُراجع قاعدة البيانات أن مجموع التوزيع يطابق العدد المسجل. السعر والعربون اختياريان، ويعرض النموذج الإجمالي المتوقع والمتبقي بعد العربون دون حقول تسليم؛ تُسجّل التسليمات من مسارها المستقل.
- بيانات الاتصال محصورة في تبويب ملفات العملاء/حسابات العملاء؛ جداول الطلبات وإدارة المستخدمين لا تعرض أرقام الهاتف. في نموذج الموديل يختار المستخدم العميل أو البراند من قائمتين منفصلتين ومتبادلتين. يمكن تحديد أقسام القص والخياطة والتشطيب والمكوى والأمبلاج والتكييس، وتسعير القطعة كسعر إجمالي أو بجمع السعر المستقل لكل قسم. تحفظ الأقسام وطريقة التسعير وتفاصيل أسعار الأقسام في `orders.work_stages`, `orders.pricing_mode`, و`orders.stage_prices`؛ ويظل سعر القطعة الإجمالي هو أساس حسابات التسليم والرصيد.

## ملفات المشروع

- `login.html`: تسجيل الدخول وإنشاء الحساب.
- `dashboards/`: لوحات الإدارة والقص والخياطة والعامل والعميل.
- `js/auth.js`: المصادقة، إرسال طلبات الحساب، وتوجيه المستخدم حسب حالته ودوره.
- `js/dashboard.js`: عرض اللوحات وإدارة تفعيل الحسابات وأوامر التشغيل ومراحل القص والخياطة والسجلات المرنة عبر Supabase.
- `js/supabase-config.js`: عنوان المشروع ومفتاح النشر العام.
- `supabase/schema.sql`: الجداول الأساسية ومخزن السجلات المرن JSONB والحسابات المرتبطة بـAuth وسياسات RLS والدوال.
- `css/styles.css`: التنسيق ودعم الشاشات الصغيرة.

## ملاحظات تشغيل

- تأكد من تعطيل **Confirm email** قبل التسجيل باسم مستخدم، كي يصدر Supabase Auth جلسة تسمح بإدراج الصف بأمان. شغّل `supabase/schema.sql` لتفعيل سياسة RLS ومنح صلاحية إدراج الأعمدة المسموحة؛ لا يحتاج هذا المسار إلى trigger.
- كلمات المرور تُدار بواسطة Supabase Auth ولا تُحفظ في جدول `users` أو في ملفات الواجهة.
- لا تصبح طلبات التسجيل والتفعيل مشتركة بين الأجهزة حتى تشغيل SQL وإعداد حساب الأدمن وإعداد البريد ونشر المشروع.
